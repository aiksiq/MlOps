## 00:00:18 — Архитектура стенда

**Экран:** 4 клиентских Pod → Service / ClientIP affinity /                      ↓ / FastAPI · SSE · ограниченная очередь · prefix cache /                      ↓ /metrics / Prometheus → Grafana и alert rules / CPU metrics → HPA: 2–3 реплики /  / kind: 1 control-plane + 2 worker · Helm Deployment

**Диктор:** Стенд состоит из локального kind-кластера: один управляющий узел и два рабочих. Helm разворачивает FastAPI, два варианта Service, мониторинг и HPA. **Диктор:** После проброса порта маршрут ready показывает готовность backend. Health, startup и ready разделены: живой процесс ещё не обязательно готов принимать нагрузку. История диалога передаётся с каждым запросом. Показанный фрагмент сокращён из реального журнала, а не изображает новый сеанс терминала.

## 00:02:55 — Задержки и очередь по Pod

**Экран:** Сопоставляем TTFC, очередь и распределение нагрузки / Средняя CPU может скрывать перегруженную реплику

**Диктор:** График задержек и очереди разбит по Pod. Он помогает увидеть перекос, который может скрыться за средней загрузкой Deployment. TTFC здесь означает время до первой содержательной части ответа. Это не время до первого токена модели. Клиентские перцентили считаются только по полностью завершённым ответам, поэтому число отказов необходимо показывать рядом. Ограничение очереди делает перегрузку явной, вместо бесконечного ожидания.

**Источник:** results/plots/02-pod-latency-queue.svg · results/b-*.csv
